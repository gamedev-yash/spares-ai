This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

See `README.md` for full documentation (setup, env vars, data model, API surface, known
limitations). This file only covers what a coding agent needs that isn't obvious from a
quick skim of the code.

## This is not the Next.js you know

Per `AGENTS.md`: this project uses a Next.js version with breaking changes vs. training
data — APIs, conventions, and file structure may differ. Read the relevant guide in
`node_modules/next/dist/docs/` before writing Next.js code, and heed deprecation notices.

## Commands

```bash
# Backend (from backend/)
./.venv/Scripts/activate                    # Windows venv
uvicorn app.main:app --reload --port 8000   # dev server, http://localhost:8000/docs for Swagger

./.venv/Scripts/python.exe -m pytest                        # full suite
./.venv/Scripts/python.exe -m pytest -q --tb=short           # quiet
./.venv/Scripts/python.exe -m pytest tests/test_rr.py         # one file
./.venv/Scripts/python.exe -m pytest tests/test_rr.py::test_name  # one test

python scripts/generate_synthetic_data.py            # regenerate backend/data/*.csv (seed 12345)
python scripts/generate_synthetic_data.py --seed 777  # different deterministic dataset

# Frontend (from repo root)
npm run dev      # http://localhost:3000
npm run build
npm run lint
npx tsc --noEmit  # no test runner wired up — this is the fastest sanity check
```

Backend and frontend must both be running for the app to work end to end (`/login`, any
API-backed page). Frontend needs `NEXT_PUBLIC_API_BASE_URL` (`.env`, from `.env.example`)
pointing at the backend.

## Architecture

```
Next.js (frontend) ──HTTP/REST──▶ FastAPI (backend) ──reads/writes──▶ CSV files (backend/data/*.csv)
```

No database, no ORM, no auth enforcement, no Docker — this is a demo/dev build.
`backend/app/services/csv_store.py` is the entire persistence layer: loads every CSV into
memory at startup; every `insert`/`update` mutates memory and immediately rewrites the file.
Not safe for concurrent writes — fine at this scale, not a pattern to extend into anything
production-shaped. Chat session/message state is the one exception: purely in-memory
(`ChatStore`), lost on backend restart.

**Two data lanes — do not conflate them:**
- `/dashboard` (VZI) and `/dashboard/situation-analysis` are fed by fixed, real reference
  numbers transcribed from an actual review-slides workbook
  (`backend/app/services/vzi_reference_data.py`, `backend/data/situation_analysis.csv`) —
  never regenerated by the seed script.
- Everything else (rr/pr/po/approvals/audit/notifications/process_stage_events) is fully
  **synthetic**, regenerated by `generate_synthetic_data.py`, and powers `/api/analytics/*`
  and the dashboard's "Live cycle time" tab.

**Repository layout:**
```
src/                      Next.js App Router
  app/                    routes: /materials /audit /dashboard /approvals /notifications /chat/... /login
  lib/api/                frontend API client, one file per backend domain
  lib/mock-data.ts        LEGACY — only backs the pre-scripted /chat/[sessionId] demo sessions
backend/
  app/api/routes/         one FastAPI router per domain
  app/schemas/            Pydantic request/response schemas
  app/services/           business logic: csv_store, approvals, RR creation, analytics, audit,
                           quality rules, vzi reference data
  app/ai/                 LLM provider abstraction, tool registry, chat orchestrator (see below)
  data/                   CSV files — source of truth, committed to the repo
  scripts/                synthetic data generator + material/supplier catalog
  tests/                  pytest suite, runs against a throwaway tmp_path CSV dir, never backend/data/
```

**AI architecture** (`backend/app/ai/`): `provider_base.py` defines the `LLMProvider`
interface; `demo_provider.py` is deterministic and needs no API key (default, `AI_MODE=demo`);
`anthropic_provider.py`/`openai_provider.py` run real tool-calling loops. `tools.py` is the
*only* way the assistant touches data — every tool handler goes through the normal backend
services/CSV store; the LLM never touches a file directly. `orchestrator.py` wires
`POST /api/chat`: demo mode is fully rule-based routing (no LLM call), provider mode hands
routing to the model's tool-calling loop. `pr_quality.py` / `services/quality_validation.py`
are deterministic rules for PR line-item quality — an optional LLM only narrates the rule
output, never decides what counts as an issue. Switching to a real model is env-var only:
`AI_MODE=provider`, `AI_PROVIDER=anthropic|openai`, matching API key.

**Auth**: none, by design for this phase. `POST /api/auth/login` returns the user's bare id
as a "token" if `employee_code` exists and is active in `users.csv`; password is accepted
but never checked. No route enforces RBAC or 401s except unknown/inactive login. Don't
"fix" this — see README §9 for the rationale.

**Errors**: every API error uses one envelope, `{"error": {"code", "message", "details"}}`;
stack traces are logged, never sent to the client.
